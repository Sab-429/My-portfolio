    Turning a number into a short code

    The API server holds a unique integer ID, then writes it in base 62. Dividing by 62 repeatedly gives the digits, and each digit maps to one character. Change the ID and watch the code rebuild.

    Alphabet: 0–9 are values 0–9, a–z are 10–35, A–Z are 36–61. The code is read from the last remainder to the first.

    Short code (7 characters)
    Divide by 62 until the quotient is 0

    The diagram above uses counter + base62 with block leasing. Each API server asks the ID service for 1,000 IDs at once, then serves them from memory, so the ID service sees one call per 1,000 new links. To hide the sequence, run the ID through a reversible shuffle before encoding.

    Reverse proxy and load balancer

    Nginx (or a cloud load balancer) is the only public entry point. It ends TLS, limits abusive callers, and spreads requests across API servers. Stop a server below. The proxy keeps sending to it until its health check fails, retries the failed request on another server, then drops it from rotation.

    # 10 create requests per second per IP, bursts of 20
limit_req_zone $binary_remote_addr zone=shorten:10m rate=10r/s;

upstream api {
    server api-1:8080 max_fails=2 fail_timeout=5s;
    server api-2:8080 max_fails=2 fail_timeout=5s;
    server api-3:8080 max_fails=2 fail_timeout=5s;
    keepalive 64;
}

server {
    listen 443 ssl;
    server_name sho.rt;
    # ssl_certificate and ssl_certificate_key go here

    location = /api/v1/shorten {
        limit_req zone=shorten burst=20 nodelay;
        proxy_pass http://api;
    }

    location / {
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_next_upstream error timeout http_502 http_503;
        proxy_pass http://api;
    }
}

    What the proxy layer does

    TLSTerminated once here, so API servers speak plain HTTP on the private network.
    Rate limitingToken bucket per IP or API key. Create is limited tightly, redirects loosely.
    BalancingRound robin works because API servers are stateless. Any server can answer any request.
    Health checksFailed upstreams are skipped for a cooling-off period.
    KeepaliveReuses connections to API servers instead of opening one per click.

    The cache that takes most of the traffic

    Redis sits beside the API servers using cache-aside. Read the cache first, go to the database only on a miss, then store the answer. With maxmemory-policy allkeys-lru, Redis evicts the key used longest ago when memory is full. A few links get most of the clicks, so a small cache covers a lot. Send requests and watch it.

    Click popularity follows a Zipf-like curve over 12 links: the first code gets the most clicks and the twelfth the fewest. Latency assumes 1 ms for a cache read and 15 ms for a database read. Those two numbers are illustrative, so measure your own.

    Redirect handler (pseudocode)
    app.get('/:code', async (req, res) => {
  const { code } = req.params;

  let url = await redis.get(code);          // 1. cache first
  if (!url) {
    const row = await replica.findOne(code); // 2. miss: read replica
    if (!row || (row.expires_at && new Date() > row.expires_at)) {
      return res.sendStatus(404);
    }
    url = row.long_url;
    await redis.set(code, url, 'EX', 86400); // 3. refill, 24h TTL
  }

  // 4. fire and forget: never wait on analytics
  kafka.send('clicks', { code, ts: Date.now() }).catch(() => {});

  res.redirect(302, url);
});

    Database, replicas and shards

    The core access pattern is one lookup by code, which fits a key-value store as well as a relational table. Postgres, MySQL, DynamoDB, Cassandra and MongoDB all work with code as the key. Writes go to a primary, cache misses read from replicas, and when one primary can no longer take the writes, split the table across shards by a hash of the code.

    Sharding by hash of the code

    3,000 sample codes are spread across the shards. The numbers show what happens when you add one more shard. Plain hash mod N reassigns most keys, which means a huge data move. Consistent hashing places shards on a ring, so a new shard takes keys from its neighbours only.

    Edge cases that break naive versions

    Custom alias clashes

    Counter IDs never collide, but a user-chosen alias can. Make code the primary key and return 409 on a unique-constraint error instead of checking first.

    Expired links

    Check expires_at on read, cap the Redis TTL at the time left, and run a batch job off-peak to delete expired rows.

    Cache stampede on a viral link

    When a hot key expires, thousands of requests miss at once. Let one request refill the cache while the rest wait, and add random jitter to TTLs.

    One hot key

    A single celebrity link can saturate one Redis node. Keep a small in-process cache on each API server for a few seconds, or replicate hot keys.

    Replica lag

    A brand-new link can 404 if read from a replica that has not caught up. The create path writes to Redis, and a miss on a recently created code can fall back to the primary.

    Bots guessing codes

    Scanners hit random codes. Cache "not found" for about a minute, rate limit by IP, and consider a Bloom filter in front of the database.

    Abuse and malware

    Accept only http and https targets, refuse to shorten your own domain to avoid loops, and check destinations against a safe-browsing list when links are created.

    Deleting a link

    Delete the row, then delete the cache key, then purge any CDN copy. Serve 410 Gone afterwards so crawlers drop it.

    Guessable sequences

    Sequential IDs let anyone enumerate links and estimate your volume. Pass the ID through a reversible shuffle before base62 encoding.

    A sensible build order

    Each step fixes the bottleneck the previous one exposes. Do not start at step 7.

    1. One API server and one Postgres. Auto-increment ID, base62 encode, 302 redirect.
    2. Redis cache-aside on the redirect path. This removes most database reads.
    3. Nginx in front with two or more API servers, health checks and rate limits.
    4. Read replicas for cache misses, keeping the primary for writes.
    5. ID block leasing so API servers stop depending on one database sequence.
    6. Kafka click events and an analytics store, so counting never slows a redirect.
    7. Shard the urls table by hash of the code once one primary cannot take the writes.
